# 코드 점검 보고서 (권한·보안 + DB 정합성)

작성: 2026-04-29 / 범위: server/ + drizzle/ + 인증·업로드·OCR + 라우터 권한 격리

> 점검 시점 코드 기준. 모든 결함은 재현·수정 모두 Claude Code 측에서 진행할 것 (Cowork 직접 수정 금지).
> CRITICAL = 운영 데이터 또는 비용에 즉각적 영향. HIGH = 매장 격리 위반(IDOR). MED = 일관성·DoS·하드닝.

---

## 0. 한 줄 요약

매장 격리(`storeReadProcedure`/`verifyStoreAccess`) 적용이 **라우터마다 들쭉날쭉**해서 IDOR이 광범위. 업로드/OCR API는 **인증 자체가 없고** path traversal 가능. 인증 토큰은 **httpOnly 쿠키가 아니라 JS-readable**. 1~3번이 가장 시급.

## 1. CRITICAL — `/api/upload/*` 인증 부재 + Path Traversal

**파일**: `server/upload.ts`

**증상**:
- `uploadRouter` 7개 엔드포인트 전부 인증 미들웨어 없음. 비로그인 누구나 호출 가능.
- 5~10MB 파일 무제한 업로드 → 볼륨/임시스토리지 소진(DoS) 또는 무단 파일 호스팅.
- `/api/upload/rotate-image`(L227) — `req.body.url`을 `path.join(UPLOAD_ROOT, url.replace(/^\/uploads\//, ""))` → `../`/절대경로 차단 없음. **임의 파일을 sharp로 회전→덮어쓰기 가능**.
- `/api/upload/order-image-replace`(L255) 동일 패턴 — `replaceUrl`로 **임의 파일 임의 이미지로 덮어쓰기**.

**영향**: 서버 측 파일 손상/덮어쓰기, 디스크 소진, 무인증 업로드 비용.

**조치**:
- Express 미들웨어로 JWT 쿠키 검증 → `req.user` 주입. 모든 `uploadRouter` 라우트에 일괄 적용.
- `relativePath` 검증: `path.resolve(UPLOAD_ROOT, p)`가 `UPLOAD_ROOT` prefix인지 확인 (`path.relative(UPLOAD_ROOT, resolved)`가 `..`로 시작 안 함).
- 매장 자원 업로드(체크리스트·발주·고정비)는 `restaurantId`를 multipart에 포함 + `verifyStoreAccess` 적용.
- 대안: 업로드 자체를 tRPC presigned-style로 옮기고, 파일 본체만 multipart로.

## 2. CRITICAL — `/api/ocr/*` 인증 부재 + 비용 폭탄 + 임의 파일 노출

**파일**: `server/ocr.ts`

**증상**:
- 15개 ocrRouter 엔드포인트 전부 인증 미들웨어 없음.
- `/api/ocr/extract-purchase`, `/extract-sales`, `/extract-health-cert` — **Anthropic Vision API 직접 호출**. 비로그인자가 ANTHROPIC_API_KEY로 무한 호출 가능 → **API 비용 폭탄**.
- `imageUrl`이 path traversal 가능 (`/uploads/../../etc/...`). 서버 임의 파일을 sharp로 처리해 **Anthropic Vision에 전송 → 응답으로 외부 노출**.

**영향**: 운영 비용, 서버 파일 외부 누출, 레이트리밋 우회.

**조치**:
- Express 인증 미들웨어 적용 (1번과 동일).
- `imageUrl` 정규화 후 `UPLOAD_ROOT` 컨테인먼트 검증.
- `restaurantId` 파라미터 받아 `verifyStoreAccess`. 매장 직원이 아니면 차단.
- 추가: per-user/매장 OCR 호출 일별 quota 체크 (`api_usage_logs` 이미 있음 — 활용).

## 3. CRITICAL — JWT를 httpOnly 쿠키로 발급하지 않음 (XSS 시 토큰 탈취)

**파일**: `server/routers/auth.ts:25-31`, `server/index.ts`(쿠키 설정 grep 결과 없음)

**증상**:
- `login`이 `{ token, user, mustChangePassword }`만 반환. 서버에서 `Set-Cookie`로 `httpOnly`/`Secure`/`SameSite` 설정하지 않음 → 클라이언트 JS가 `document.cookie`에 직접 기록한다는 뜻. **XSS 한 번이면 30일짜리 토큰이 도난된다.**
- `logout`은 `{ ok: true }` 빈 응답 — 서버 측 토큰 무효화 없음(JWT 한계). 블랙리스트/회전 미구현 → **로그아웃 후에도 토큰 30일 유효**.
- `JWT_SECRET || "dev-secret-change-me"` (auth.ts:4) — env 누락 시 prod에서 약한 시크릿로 동작. fail-fast 없음.
- `verifyToken`이 `payload as unknown as TokenPayload`로 캐스팅만 함. role/userId 형 zod 검증 없음.

**영향**: 토큰 탈취 시 30일간 무한 권한 사용. 환경변수 사고 시 토큰 위조 가능.

**조치**:
- `login` 응답에서 `Set-Cookie: session=<jwt>; HttpOnly; Secure; SameSite=Lax; Max-Age=...`로 발급. 토큰 본문은 응답에서 제거(또는 클라이언트는 `me`로만 신원 확인).
- `logout`에서 `Set-Cookie: session=; Max-Age=0` 클리어.
- `JWT_SECRET` 미설정이면 prod에서 `process.exit(1)`.
- `verifyToken`에 zod 스키마(`TokenPayloadSchema.parse(payload)`) 검증.
- 로그인 레이트 리밋(같은 IP/username 5분 5회 이상 차단). 현재 없음.

## 4. HIGH — `counterpartyItems.ts` 매장 격리 전무 (IDOR)

**파일**: `server/routers/counterpartyItems.ts`

**증상**: 6개 procedure 모두 `protectedProcedure` 단순 사용. `verifyStoreAccess`/`requireStoreManager` 미호출.
- `listByCounterparty(counterpartyId)` — 임의 매장 거래처 품목 매핑 조회.
- `create({restaurantId, ...})` — 임의 매장 ID로 매핑 생성.
- `linkToExistingItem({counterpartyItemId, itemId})` — 소유 검증 없이 다른 매장 매핑 변조.
- `update({id, ...})` / `delete({id})` — counterpartyItem.id만으로 변조/삭제. 다른 매장 데이터 파괴 가능.

**조치**: 전부 `storeReadProcedure`/`storeWriteProcedure`로 교체. id 기반 mutation은 사전에 그 행의 `restaurantId`를 SELECT → ctx.restaurantId와 일치 검증 후 업데이트.

---

## 5. HIGH — `storeClosures.ts` 매장 격리 전무 (IDOR)

**파일**: `server/routers/storeClosures.ts`

**증상**:
- `listByMonth`/`getWeeklyClosures` (protectedProcedure) — 로그인만 있으면 임의 매장 휴무 조회.
- `create`/`setWeeklyClosures` (managerProcedure) — managerProcedure는 **"어느 매장이라도 owner/supervisor면 통과"**. 자기 매장 점장이 다른 매장에 휴무 등록 가능.
- `delete({id})` — id만 받음. 점장 권한 가진 사용자가 임의 매장 휴무일 삭제 가능.

**조치**: 전부 `storeReadProcedure`/`storeManagerProcedure`로 교체. delete는 사전 SELECT로 restaurantId 일치 검증.

---

## 6. HIGH — `items.ts` 매장 격리 누락 (IDOR + 데이터 파괴)

**파일**: `server/routers/items.ts`

**증상**:
- `list`/`create`/`searchSimilar` (protectedProcedure + restaurantId) — 격리 없음.
- `update({id, ...})` — id만 받음. **다른 매장 품목 이름·isActive 변경 가능**. isActive=false면 매입/레시피 연쇄 영향.
- `merge({targetId, sourceIds})` (managerProcedure) — 매장 격리 없음. 점장 권한자가 **다른 매장 품목들을 자기 매장 품목으로 흡수 가능**. counterparty_items / purchase_order_items_v2의 itemId가 통째로 바뀌어 **타 매장 회계 깨짐**.
- `findSimilarGroups` (managerProcedure + restaurantId) — managerProcedure는 매장 무관. 다른 매장 품목 그룹 노출.

**조치**: list/create/searchSimilar/findSimilarGroups → `storeReadProcedure`/`storeManagerProcedure`. update/merge → 대상 itemId의 restaurantId를 ctx.restaurantId와 비교 후 진행. merge는 sourceIds 전부 같은 매장인지 추가 검증.

## 7. HIGH — `fixedCosts.ts` update/deactivate WHERE 누락

**파일**: `server/routers/fixedCosts.ts:96, 104`

**증상**: `requireStoreManager(input.restaurantId)` 검증은 하지만 SQL은 `WHERE id = input.id`만 — `restaurantId` 조건 빠짐.
- 공격자가 자기 매장 점장 권한으로 input.restaurantId=자기매장, input.id=다른매장의fixedCostId를 보내면 → 권한 검증 통과 → 업데이트는 다른 매장 행에 적용. **타 매장 고정비 변조/비활성**.

**조치**: `WHERE id = ? AND restaurantId = ?` 2조건 모두 걸기 (counterparties.ts와 동일 패턴). 더 안전하게는 `storeManagerProcedure` 도입 후 `ctx.restaurantId` 사용.

## 8. HIGH — `verifyStoreAccess`가 사업그룹(ownerAdminId) 격리 안 함

**파일**: `server/middleware/storeAuth.ts:27-32`

**증상**: admin은 매장 배정 무관하게 **항상 read 통과**. 다른 admin(다른 사업그룹)의 매장도 읽을 수 있음. CLAUDE.md §12에서 `restaurants.ownerAdminId`로 사업그룹 격리한다고 했으나 검증 코드 없음.

**영향**: 한 admin이 타 사업그룹 매장 매출/매입/직원/계약서 전부 조회 가능 (mutation은 배정 필요해서 막힘).

**조치**: admin 분기에서 `restaurants.ownerAdminId === ctx.user.userId` (또는 `parentId` 체인 포함) 체크. master만 무제한 통과.

## 9. HIGH — `errorLogs.report`가 publicProcedure로 무제한 호출 가능

**파일**: `server/routers/errorLogs.ts:10-30`

**증상**: 비로그인 누구나 메시지 2KB + stack 5KB + metadata JSON을 무한 insert. 레이트 리밋 없음. **DB DoS / 디스크 소진**.

**조치**: 
- 옵션 A: `protectedProcedure`로 바꾸고, 비로그인 에러는 클라이언트에서 보존했다가 로그인 후 전송.
- 옵션 B: IP 기반 토큰버킷(memory or Redis). 현실적으로 A가 단순.

## 10. MED — `managerProcedure`/`ownerProcedure`가 매장 격리 안 함

**파일**: `server/trpc.ts:42-89`

**증상**: 두 프로시저는 **"사용자가 어느 매장이든 해당 역할이면 통과"**. 라우터가 input.restaurantId를 별도 검증하지 않으면 cross-store 누수. 4·5·6·7번 결함의 근본 원인.

**조치**: 매장 자원 라우터는 `managerProcedure` 대신 `storeManagerProcedure`/`storeOwnerProcedure`를 사용한다. 가이드라인을 `server/trpc.ts` 상단 주석 + `docs/`에 명문화. 신규 매장 자원 라우터는 storeXxx 프로시저만 허용한다는 ESLint custom rule 도입 검토.

## 11. MED — Legacy `purchases` 라우터 잔존

**증상**: CLAUDE.md "현재 v2"라 했지만 legacy `purchases`가 살아 있고 라우터에 등록되어 있을 가능성. 권한 검증 패턴 v2와 다름. 프론트가 어딘가 호출 중일 수도 있음.

**조치**:
- `routers/index.ts`/클라이언트에서 호출 grep → 미사용이면 제거.
- 사용 중이면 v2와 동일 격리 적용 후 deprecation 일정 결정.

## 12. MED — `mysql.createConnection` 11곳 (풀 미재사용)

**파일**: `server/index.ts`(9), `server/ocr.ts`(1), `server/routers/system.ts`(1)

**증상**: `db.ts`에 `createPool` 있지만 위 11곳은 `createConnection` 직접 호출. 마이그레이션은 단발이라 OK. 그러나 `ocr.ts:1043`, `system.ts:445`는 런타임 호출 → **요청마다 새 연결 → 누수·성능**. 또한 raw 쿼리 사용 시 input 보간 검증 별도 필요.

**조치**:
- 모든 런타임 호출은 `import { pool } from "./db"`로 통일. 마이그레이션도 가능하면 풀 사용.
- raw 쿼리는 placeholder만 사용(이미 그런 것 같지만 11곳 전부 검증).

## 13. MED — 자동 마이그레이션과 `drizzle/schema.ts` 정합성 미검증

**파일**: `server/index.ts`(2000+줄, ALTER TABLE/CREATE TABLE 산재)

**증상**: 스키마 변경이 자동 마이그레이션과 schema.ts 양쪽에 수기로 반영되어야 함. 한 쪽 누락 시 prod 부팅 실패 또는 런타임 SQL 오류. 정합성 자동 검증 없음.

**조치**:
- CI에 정적 검사 추가: schema.ts 컬럼 set vs 마이그레이션 ALTER set 비교 스크립트.
- 중기적으로 drizzle-kit migrate로 일원화 (현재 자동 ALTER는 idempotent라 동작은 함, 그러나 신뢰성 낮음).

## 14. MED — 비밀번호 정책 약함 + 로그인 레이트 리밋 없음

**파일**: `server/routers/auth.ts:36`, 동 파일 login

**증상**:
- `newPassword: z.string().min(4)` — 4자 허용. 무차별 대입 쉬움.
- 로그인 레이트 리밋 없음. bcrypt(rounds=10)이 약간의 자연 throttle 역할은 함.
- 새 비밀번호가 기존과 동일해도 통과.

**조치**: min(8) + 영문/숫자 혼합 정도. IP+username 단위 5분 10회 제한. 현재 비밀번호와 동일 차단.

## 15. LOW — 기타

- `auth.ts:logout` 서버측 처리 없음 → 토큰 회수 불가(3번에서 다룸).
- `recipes.ts`/`storeInfo.ts`/`schedules.ts`/`purchasesV2.ts` 등 store* 프로시저 사용처도 **id 기반 mutation에서 restaurantId 사전 검증** 패턴이 일관되게 들어갔는지 추가 점검 필요(이번 라운드 미수행).
- `restaurants.ownerAdminId` 변경/삭제 시 cascade 정책 미확인.
- 클라이언트 `errorReporter` ↔ `errorLogs.report` 페이로드 사이즈 제한이 서버측 z.string().max만 의지. multipart 우회 시 다른 라우트로 들어갈 가능성 별도.
