# OCR 매입 프로세스 개선 기획서

> 작성일: 2026-03-29
> 대상: 청계산뚝배기 수제비 천호점 3월 매입자료 (34장)
> 목적: OCR 정확도 검증 및 매입 프로세스 자동화 고도화

---

## 1. 현행 시스템 분석

### 1.1 현재 OCR 파이프라인

```
사진 촬영 → 클라이언트 리사이즈(2560px, 0.92) → 서버 업로드
→ Anthropic Claude Vision API (claude-sonnet-4) → JSON 파싱
→ 합계 검증 + 신뢰도 산정 → 거래처 품목 DB 매칭 → UI 자동 채움
```

**현재 강점:**
- Claude Vision API 자체의 높은 한국어 OCR 능력
- 합계 크로스체크 (수량×단가 vs 공급가액, 품목합산 vs 문서합계)
- VAT 패턴 자동 감지 (1.08~1.12 비율)
- 거래처 DB 기반 단가 이상 감지 (±30%)
- uncertain 마킹 → UI에서 노란색 하이라이트
- 사용자 수정 데이터 축적 (ocr_corrections 테이블)

**현재 구조적 결함:**
- 이미지 전처리 없음 (회전 보정, 크롭 등)
- 프롬프트에 회전된 이미지 처리 지시 없음
- 거래처별 양식 학습 기능 없음
- OCR 결과 캐싱/재시도 로직 없음
- 멀티페이지 전표 미지원

### 1.2 핵심 전제: 거래처 ↔ 양식 관계

**거래처별 양식은 사실상 고정이다.**
- 블루앤씨(주) → 항상 거래명세표(0855) 양식 사용
- 두부/묵 업체 → 항상 거래명세서(수기 혼합) 양식 사용
- 한 거래처가 양식을 바꾸는 경우는 극히 드물다

**하지만 신규 거래처 = 새 양식 유형이 될 수 있다.**
- 식자재 유통업체마다 자체 전표 양식을 사용
- 새 거래처가 추가될 때마다 처음 보는 양식이 올 수 있다
- 영수증, POS 출력물, 배달앱 정산서 등 완전히 다른 문서 유형도 가능

→ 이 특성을 활용하면: **거래처가 확정되는 순간 양식 구조도 예측 가능**하며,
신규 양식은 최초 1~2회 수정 후 학습하여 이후 자동화할 수 있다.

### 1.3 실제 이미지 분석 결과 (34장 시각 검토)

| 분석 항목 | 결과 |
|----------|------|
| 문서 유형 | 거래명세표(0855) ~85%, 거래명세서(수기혼합) ~15% |
| 정방향 촬영 | ~15% (5장 미만) |
| 90° 회전 | ~75% (대부분) |
| 180° 뒤집힘 | ~10% (3~4장) |
| 그림자 포함 | ~60% |
| 배경 노이즈 | ~30% (키보드, 메뉴판, 음식사진) |
| 거래처 수 | 최소 3개 (블루앤씨, 두부/묵 업체, 기타) |
| 평균 품목 수 | 3~10개/전표 |
| **거래처↔양식 일치** | **100% (동일 거래처는 동일 양식)** |

### 1.4 예측되는 OCR 실패 패턴

| 실패 유형 | 예상 빈도 | 원인 |
|----------|----------|------|
| 회전된 문서 열 혼동 | 높음 | 90°/180° 회전 시 열 순서 오인식 |
| 수량↔단가 뒤바뀜 | 중간 | 회전된 표에서 열 위치 혼동 |
| 거래처명 미탐지 | 중간 | 회전+잘림으로 상단 헤더 인식 실패 |
| 품목명 오인식 | 낮음~중간 | 긴 규격명, 작은 폰트, 그림자 |
| 합계행 품목 혼입 | 낮음 | 합계/소계 행을 일반 품목으로 인식 |
| 빈 결과 반환 | 낮음 | 극심한 회전+저화질 조합 |

## 2. 개선안 — 우선순위별 3단계

### Phase 1: 즉시 적용 가능 (코드 수정만, 1~2일)

#### 2.1 프롬프트 강화 — 회전 이미지 대응
**완료 조건:** 프롬프트에 회전 처리 지시 추가, 테스트 통과

현재 프롬프트에 회전 관련 지시가 전혀 없다. Claude Vision은 회전된 이미지도 읽을 수 있지만, 표의 열 순서를 정확히 파악하려면 명시적 가이드가 필요하다.

```
## 이미지 방향 주의사항 (추가할 섹션)

이미지가 회전되어 있을 수 있습니다:
- 90° 시계방향/반시계방향 회전
- 180° 뒤집힘 (상하반전)
- 약간의 기울어짐

**반드시 문서의 텍스트 방향을 먼저 파악하세요.**
거래명세표/거래명세서의 제목이 어느 방향에 있는지 확인한 후,
그 기준으로 열(컬럼)을 왼→오 순서로 읽으세요.
열 순서 오류는 전체 데이터를 무효화합니다.
```

#### 2.2 프롬프트 강화 — 문서 양식 세분화 + 확장 가능 구조
**완료 조건:** 현재 확인된 양식 + 신규 양식 대응 프레임워크

현재 확인된 양식 2종을 기본 가이드로 넣되, 새 양식이 추가될 수 있음을 전제로 설계한다.

```
## 양식별 열 구조 (추가할 섹션)

**[유형A] 거래명세표 (0855 양식) — 가장 흔함:**
- 좌측: 공급자 정보, 우측: 공급받는자 정보
- 열: 월일 | 품목/규격 | 단위 | 수량 | 단가 | 공급가액 | 부가세 | 비고
- 하단: 합계 + 인수자 서명란
- 특징: 인쇄된 표 양식, 사업자등록번호 2개 표시

**[유형B] 거래명세서 (수기/인쇄 혼합):**
- 상단: 거래명세서 제목 + 날짜 + 도장
- 열: 품명 | 규격 | 수량 | 단가 | 공급가액
- 구조가 단순하고 품목 수가 적은 편
- 특징: 빨간 도장, 수기 기입 혼합

**위 유형에 해당하지 않는 새로운 양식인 경우:**
- 열 헤더를 먼저 읽어 열 순서를 파악하세요
- documentType을 "기타"로 설정하세요
- 열 구조를 note 필드에 기록하세요 (예: "품명|수량|금액 3열 구조")
```

→ Phase 2에서 `counterparty_ocr_profiles`에 양식 유형이 저장되면,
거래처 확정 시 해당 유형의 프롬프트만 선택적으로 주입하여 토큰 절약 + 정확도 향상.

#### 2.3 서버사이드 검증 강화 — 기존 거래 데이터 크로스체크
**완료 조건:** 추가 검증 로직 통과

기본 검증:
- 수량이 100 이상인 경우 → confidence "medium" (단가와 혼동 가능성)
- 단가가 수량보다 작은 경우 → confidence "low" (열 뒤바뀜 의심)

**기존 거래 데이터 기반 검증 (현재도 부분 구현됨, 강화 필요):**
- `counterparty_items.price` 대비 OCR 단가 ±30% → confidence "low" (현재 구현)
- **추가**: 해당 거래처에서 한 번도 거래한 적 없는 품목 → "신규 품목" 마크
- **추가**: 최근 3개월 발주 이력 기준, 수량 패턴 이탈 감지 (평소 2박스인데 20박스 → 확인 필요)
- **추가**: 동일 거래처 이전 발주 대비 총액 ±50% → 경고 표시
- **추가**: 거래처 프로파일의 `columnOrder`와 OCR 결과의 열 순서가 맞는지 교차 검증

### Phase 2: 클라이언트 개선 (3~5일)

#### 2.4 이미지 회전 UI 추가
**완료 조건:** OCR 전 사용자가 90°/180° 회전 가능, 회전 후 OCR 재실행

현재 촬영 후 바로 OCR이 실행되는데, 사용자가 이미지를 확인하고 회전을 보정할 수 있는 단계가 없다.

구현:
- OCR 전 미리보기 단계 추가
- 90° 회전 버튼 (시계/반시계)
- Canvas API로 클라이언트에서 회전 처리
- 회전 후 OCR 실행

#### 2.5 OCR 결과 신뢰도 시각화 개선
**완료 조건:** 품목별 confidence 컬러 + 수정 제안 표시

- high: 기본 (수정 불필요)
- medium: 노란 배경 + "확인 필요" 라벨
- low: 빨간 테두리 + "수정 필요" 라벨 + 가능한 대안 표시
- 수량×단가 ≠ 금액인 경우 → 자동 계산값 제안 표시

#### 2.6 거래처별 양식 프로파일 시스템
**완료 조건:** 거래처 선택 시 양식 유형 자동 적용 + 기존 품목 제안

**핵심 전제**: 거래처별 양식은 고정이므로, 한 번 확인된 양식 구조를 DB에 저장하고 재사용한다.

DB 설계 — `counterparty_ocr_profiles` 테이블:
```
counterpartyId  INT       — 거래처 FK
documentType    VARCHAR   — 거래명세표|거래명세서|영수증|POS|배달정산서|...
columnOrder     JSON      — 열 순서 (예: ["품목","단위","수량","단가","공급가액","부가세"])
hasVat          BOOLEAN   — 부가세 별도 여부
hasSummaryRow   BOOLEAN   — 하단 합계행 존재 여부
sampleImageUrl  VARCHAR   — 참고용 양식 샘플 이미지
customPromptHint TEXT     — 이 거래처 전용 OCR 힌트 (자동 축적)
confirmedAt     DATETIME  — 사용자 확인 시각
```

동작 흐름:
1. OCR 실행 → 거래처명 탐지 → DB에서 해당 거래처의 프로파일 조회
2. **프로파일 존재**: 열 순서/양식 정보를 프롬프트에 주입하여 정확도 극대화
3. **프로파일 미존재 (신규 거래처)**: 기본 프롬프트로 1차 추출 → 사용자 수정 후 양식 프로파일 자동 생성
4. 사용자가 수정한 패턴이 누적되면 `customPromptHint` 자동 갱신

추가 기능:
- 거래처 선택/탐지 후, 해당 거래처의 기존 품목 목록 로드
- OCR 결과의 shortName을 기존 품목과 fuzzy 매칭
- 매칭된 품목의 이전 단가를 참고값으로 표시
- 신규 품목은 "새 품목" 마크 표시

### Phase 3: 시스템 고도화 (1~2주)

#### 2.7 거래 데이터 기반 동적 프롬프트 주입
**완료 조건:** 거래처 확정 시 기존 거래 데이터를 OCR 프롬프트에 자동 주입

**이미 축적된 데이터 소스 3가지:**
1. `counterparty_items` — 거래처별 품목 마스터 (name, price, unit)
2. `purchase_orders_v2` + `purchase_order_items_v2` — 과거 발주 이력 (품목, 수량, 단가, 날짜)
3. `ocr_corrections` — 사용자 수정 이력 (원본→수정 diff)

**동적 프롬프트 주입 설계:**

거래처가 탐지/선택되면 OCR 프롬프트에 다음을 추가 주입:

```
## 이 거래처의 기존 거래 데이터 (참조용)

거래처: 블루앤씨(주)
양식: 거래명세표(0855), 열순서: 품목|단위|수량|단가|공급가액|부가세

최근 거래 품목 (품명 → 일반 단가 → 단위):
- 콘시윌이잼 → 13,800원 → 박스
- 다진마늘(국산) → 7,000원 → kg
- 철리소스 → 6,500원 → EA
- 실곤약 → 94,405원 → 묶

이 품목들이 이미지에 있으면 위 품명으로 shortName을 통일하세요.
단가가 위 범위에서 ±30% 이상 차이나면 uncertain: true로 마킹하세요.
```

**구현 흐름:**
1. OCR 1차 실행 → 거래처명 추출
2. 거래처명으로 DB 조회 → `counterparty_items` + 최근 3개월 발주 이력
3. 양식 프로파일(`counterparty_ocr_profiles`) 조회
4. 위 데이터를 프롬프트 후반부에 주입하여 2차 OCR 실행 (또는 1차에서 바로 주입)
5. 거래처가 UI에서 미리 선택된 경우 → 1차부터 바로 주입 (2회 호출 불필요)

**최적화 — 2회 호출 방지:**
- 사용자가 거래처를 **먼저 선택**한 후 OCR 촬영하면 → 1회 호출로 완료
- 거래처 미선택 상태에서 촬영하면 → 1차 기본 → 거래처 탐지 → 필요시 2차 보강
- UI에서 "거래처 먼저 선택" 유도 (거래처 드롭다운을 OCR 버튼 위에 배치)

**수정 이력 자동 학습:**
- `ocr_corrections`에서 동일 거래처의 반복 수정 패턴 분석
- 예: "A거래처는 항상 수량과 단가가 뒤바뀜" → `customPromptHint`에 자동 추가
- 품목명 OCR→실제 매핑 테이블 자동 생성 (예: "콘시윌이잼" ← "콘시월이잼")

#### 2.8 멀티 이미지 합산
**완료 조건:** 한 거래처의 여러 전표를 하나의 매입으로 합산

실제 데이터를 보면 같은 거래처의 전표가 여러 장인 경우가 많다 (같은 날짜, 같은 사업자번호). 현재는 전표 1장 = 매입 1건이지만:

- 같은 날짜 + 같은 거래처 자동 감지
- "합산" 버튼으로 여러 전표의 품목을 하나로 머지
- 중복 품목 자동 합산 (수량 합계)

#### 2.9 배치 OCR 모드
**완료 조건:** 여러 장 연속 촬영 → 일괄 OCR → 일괄 확인

월말 정산 시 수십 장의 전표를 한 번에 처리해야 하는 시나리오:

1. 연속 촬영 모드 (카메라 닫지 않고 계속 촬영)
2. 큐에 쌓인 이미지 순차 OCR 처리
3. 결과 리스트에서 일괄 확인/수정
4. 전체 확정 시 한 번에 저장

## 3. 비용 분석

### API 호출 비용 (Claude Sonnet 4)

| 항목 | 값 |
|------|-----|
| 이미지 입력 | ~1,600 토큰/장 (2560px 기준) |
| 프롬프트 | ~800 토큰 |
| 출력 | ~500~2,000 토큰/장 |
| 단가 (입력) | $3/M tokens |
| 단가 (출력) | $15/M tokens |
| **장당 비용** | ~$0.01~0.04 |
| **월 100장 기준** | ~$1~4/월 |

→ 비용 면에서 현행 Sonnet 4 유지가 합리적. Haiku로 변경 시 정확도 하락 리스크가 비용 절감보다 큼.

## 4. 테스트 실행 가이드

### 4.1 테스트 스크립트 사용법

Google Drive에서 이미지를 서버에 다운로드 후:

```bash
# 전체 테스트
npx tsx scripts/ocr-test.ts uploads/ocr-test/

# 단일 이미지 테스트
npx tsx scripts/ocr-test.ts --single uploads/ocr-test/20260327_132933.jpg
```

결과 파일:
- `scripts/ocr-test-results.json` — 품목별 상세 JSON
- `scripts/ocr-test-report.txt` — 사람이 읽을 수 있는 리포트

### 4.2 수동 검증 체크리스트

각 이미지별로 확인할 항목:

- [ ] 거래처명이 정확히 추출되었는가?
- [ ] 품목 개수가 원본과 일치하는가?
- [ ] 합계/소계 행이 품목에 혼입되지 않았는가?
- [ ] 수량 열과 단가 열이 뒤바뀌지 않았는가?
- [ ] 공급가액이 수량×단가와 일치하는가?
- [ ] 문서 합계와 품목 합산이 일치하는가?
- [ ] uncertain 마킹이 적절한가?

### 4.3 기준 지표 (KPI)

| 지표 | 현재 추정 | Phase 1 목표 | Phase 2 목표 | Phase 3 목표 (학습 후) |
|------|----------|-------------|-------------|---------------------|
| 거래처명 정확도 | 70~80% | 90%+ | 95%+ | 99%+ (프로파일 매칭) |
| 품목 수 일치율 | 80~90% | 95%+ | 98%+ | 99%+ |
| 수량 정확도 | 75~85% | 90%+ | 95%+ | 98%+ (기존 데이터 보정) |
| 단가 정확도 | 75~85% | 90%+ | 95%+ | 98%+ (기존 데이터 보정) |
| 금액 정확도 | 80~90% | 95%+ | 98%+ | 99%+ |
| 수정 없이 확정 비율 | 30~50% | 60%+ | 80%+ | **90%+ (기존 거래처)** |
| 신규 거래처 1회차 정확도 | — | — | — | 70%+ (학습 전 기본값) |
| 신규 거래처 2회차~ 정확도 | — | — | — | 90%+ (프로파일 생성 후) |

## 5. 즉시 실행 단계

1. **테스트 스크립트 배포**: `scripts/ocr-test.ts`를 Railway에 push
2. **Google Drive 이미지 다운로드**: 34장을 서버 `uploads/ocr-test/`에 배치
3. **테스트 실행**: `npx tsx scripts/ocr-test.ts uploads/ocr-test/`
4. **리포트 분석**: 실제 정확도 수치 확인
5. **Phase 1 프롬프트 수정**: 회전 대응 + 양식 세분화
6. **재테스트**: 프롬프트 수정 후 동일 이미지로 비교
7. **Phase 2 착수 여부 결정**: 정확도 기준 충족 시 UX 개선으로 전환
