> 작성: 2026-05-02 (Cowork)
> 상태: 사양 확정 대기 (사용자 검토 후 Code 핸드오프)
> 트리거: LaborCostPage에서 월급제 직원 합계가 계약월급과 다른 값(예: 270만 → 225만/176만)으로 표시. 시간 부족 시 자동 차감, 표시값 ≠ 실제 지급액 괴리 발생.

## 0. 핵심 판단

월급제는 본질적으로 **고정급 + 명시적 차감만 허용**하는 임금 형태다. 현재 시스템은 매 시프트마다 시급 환산 후 누적해 합계로 사용한다 → 시급제와 동일한 운영 → 월급제의 정의 위배.

5인 미만/이상은 **연차 발생 의무 유무**에만 영향한다. 분모(소정근로시간)·휴무일 수·시급 가이드·합계 산식은 5인 여부와 무관하다.

해결 방향: **합계 = 계약월급 - 미근무시간 차감(시간 비례) - 입사·퇴사 일할 보정**, **분모는 209h로 통일**, **5인 여부는 연차 발생 추적에만 적용**.

## 1. 현재 결함 (재진단)

### 1.1 월급제 합계 = 시간 비례 누적
`server/routers/schedules.ts:1080-1117`:
```
let stdHours = computeMonthlyStandardHours(null, true); // 209h fallback
...
const wage = computeWageForShift({
  wageType: 'monthly',
  wageAmount: 월급,
  hoursWorked: hours,
  monthlyStandardHours: stdHours,
});
companyMap[company].employees[empKey].totalWage += wage;  // ← Σ 누적
```
시프트마다 `시간 × (월급/분모)`를 누적해 `totalWage` 산출. 결과:
- 김정란(월급 270만, 218h, 5인 미만 분기 적용 분모) → 합계 2,257,644원 (-16.4%)
- 진재이(월급 320만, 144h) → 합계 1,767,452원 (-44.8%)

월급제임에도 시간 부족 시 임금이 자동 차감됨.

### 1.2 분모 5인 분기
`StaffPage.tsx:1775`:
```
const divisor = monthlyContractHours + (form.over5Employees ? 8 : 0);
```
5인 이상에 +8h 가산하는 분기. 사용자 의사: 분모는 5인 여부와 무관하게 209h 통일.

### 1.3 표시값 ≠ 지급액
`emp.effectiveMonthly = emp.totalWage` (schedules.ts:1210) → 합계가 곧 "실효 월급"으로 표시되지만 실제로는 계약월급에서 시간 비례로 깎인 값. 운영자가 "이 금액 그대로 지급"으로 오해할 위험.

### 1.4 일할/결근 정책 부재
- 입사·퇴사 월의 일할 계산 식 없음. 시프트가 적게 잡힌 결과로 합계만 작아짐.
- 결근일을 명시적으로 입력할 UI·필드 없음. 시프트 부재 = 결근 vs 운영 누락 구분 불가.

## 2. 새 정산 룰

### 2.1 5인 여부의 영향 범위 (재정의)

| 영역 | 5인 이상 | 5인 미만 |
|---|---|---|
| 분모 (소정근로시간) | **209h** | **209h** |
| 시급 가이드 | 월급 ÷ 209 | 월급 ÷ 209 |
| 일급 가이드 | 시급 × 8 | 시급 × 8 |
| 월급 가이드 | 계약월급 | 계약월급 |
| 합계 산식 | **§2.2 단일 산식** | **§2.2 단일 산식** |
| 연차 자동 발생 | 적용 (입사일 기준) | 미적용 (포괄수당) |
| 주휴 | 209h 분모에 이미 포함 | 209h 분모에 이미 포함 |

→ 5인 분기는 **연차 발생 로직 한 곳에만** 잔존. 그 외 모든 임금 산정·표시 코드에서 5인 분기 제거.

### 2.2 월급제 합계 산식

```
합계 = 계약월급
       - 일할 보정 (입사·퇴사 월에만)
       - 미근무시간 차감
```

상세:

#### (a) 일할 보정 (입사·퇴사 월)
- 입사 월: `월급 × (입사일 ~ 월말 일수) / 월간 일수`
- 퇴사 월: `월급 × (월초 ~ 퇴사일 일수) / 월간 일수`
- 동월 입·퇴사: 두 비율의 곱 적용
- 그 외 월: 일할 미적용 (= 계약월급 그대로)

월간 일수는 **달력일수**(28~31). 소정근로일 기반은 휴무일 정의가 변동성 있어 분쟁 소지.

#### (b) 미근무시간 차감 (시간 기준 — 사용자 결정)
```
미근무시간 = max(0, 소정근로시간_월 - 실근무시간)
미근무차감 = 미근무시간 × (월급 / 209h)
```

- 소정근로시간_월 = 209h (또는 일할 보정 시 209h × 일할비율)
- 실근무시간 = 시프트 합산
- 합계는 0원 미만으로 내려가지 않음 (`max(0, …)`)

> 사용자 결정 (a 옵션): "미근무시간 × (월급/209) 차감" — 결근일을 별도로 입력하지 않고 시프트 부재 시간만큼 자동 차감. 운영자가 시프트를 빠뜨리면 임금이 깎이는 위험은 있으나, 결근 입력 UI 신설 비용 회피 + 시프트 = 사실상 출퇴근 기록 SSOT라는 운영 전제.

#### 검증식
- 시프트 합산이 209h 이상이면 미근무차감 = 0 → 합계 = 계약월급
- 시프트 합산이 209h 미만이면 부족분만큼 시급 비례 차감
- 입사·퇴사 월은 209h를 일할 비율로 축소한 값과 비교

### 2.3 가이드 환산 (LaborCostPage 표시)

월급제 직원:
- 시급 가이드 = 월급 ÷ 209
- 일급 가이드 = 시급 × 8
- 월급 가이드 = 계약월급
- 5인 여부에 따른 분모 차이 표기 **제거** ("5인 미만 — 연차 분모 제외" 라벨 삭제)

실효:
- 실효 시급 = 합계 ÷ 실근무시간
- 실효 일급 = 합계 ÷ 실근무일수
- 실효 월급 = 합계
- 가이드와 다른 경우 차이율(±%) 표시 유지

### 2.4 시급제는 본 사양 범위 외

시급제는 현행 산식(시간 × 시급 + 주휴 별도/포함 분기) 유지. 본 사양은 월급제 합계 결함만 다룸.

### 3.4 일별 박제 ↔ 월말 일괄 정합 (구조 결함, 1차 보고 누락분)

**결함**: §2.2 합계 산식은 월 단위 일괄(`209h × ratio - shortfall × 월급/209`)이지만 시스템은 일별 박제(`daily_closings.laborCost`)를 전제로 동작. 결과적으로 두 화면이 서로 다른 산식을 본다.

| 화면 | 데이터 소스 | 산식 |
|---|---|---|
| LaborCostPage | `schedules.laborCostByCompany` 실시간 | 신 사양 (월말 일괄) |
| MonthlySettlementPage | `daily_closings.laborCost` SUM | **구 사양** (일마감 시점 시간 비례 박제) |
| 일마감 추정 | `dailyClosings.estimate` | **구 사양** (시프트 단위 누적) |

→ Phase 1~3만 적용하면 LaborCostPage는 정상화되지만 월정산은 구 산식 박제값을 그대로 SUM. 화면 간 괴리.

**해결 방향: 일별 박제는 시급/일급/임시만, 월급제는 월말 일괄**

원칙:
- 월급제(고정급)와 시급제(시간 비례)의 본질적 차이를 시스템에 반영
- 일별 박제는 *시간 비례 임금*에만 의미 있음 → 시급제·일급제·임시 직원만 박제
- 월급제는 일별 박제 = 0, 월정산 시점에 `laborCostByCompany` 산식 재사용해 합산

수정 대상:
- `dailyClosings.estimate`: 월급제 시프트 wage=0 (시급제·일급제·임시만 누적)
- `dailyClosings.save`: 월급제 박제값 0 강제 (또는 사용자 입력 분리)
- `monthlyClosings.sumLaborByCompany`: 박제 SUM(시급/일급/임시) + 월말 월급제 일괄 산출 합산
- `MonthlySettlementPage`: 인건비 출처 분리 표시 검토 (선택)

테스트:
- 한 매장에 월급제 1명 + 시급제 2명 → daily_closings에 시급제 2명만 박제 → 월정산에서 + 월급제 1명 합산
- 일마감 미진행 날짜: 월급제는 영향 없음 (월말 일괄), 시급제는 unconfirmed 추정 그대로
- LaborCostPage 인건비 = MonthlySettlementPage 인건비 일치

### 3.6 기존 박제값 호환성 — 5월 일마감 재산출 (Phase 5 push 차단 결함 대응)

**결함**: `monthlyClosings.sumLaborByCompany`의 박제 안전망(§4.7)에서 `ratio = snapshotTotal / shiftTotalCost` 보정이 동작하는데, cda02e6 배포 이전에 박제된 `daily_closings.laborCost`는 옛 산식(월급제 시간 비례 포함). 새 코드는 `shiftTotalCost`에 월급제를 제외하므로 ratio가 부풀려져 시급제 amountShifts가 비현실적으로 커짐. 거기에 `monthlyTotalCost`까지 가산 → 총합 어긋남, 사양 정반대 결과.

**대응 (사용자 결정 A)**: 5월 일마감 박제값을 신 산식으로 강제 재산출 후 push.

#### 절차
1. master 권한 스크립트 `scripts/recompute-daily-closings-2026-05.ts` 신설 (1회성)
2. 대상: `daily_closings.closingDate >= '2026-05-01' AND closingDate < '2026-06-01'` 모든 row (전 매장. 천호점뿐 아니라 다른 매장도 동일 결함 영향 받으므로)
3. 각 row의 `closingDate` 기준으로 `dailyClosings.calculateDay`(Phase 5 적용분)와 동일 로직으로 인건비 재산출
4. dry-run: 변경 전·후 값 + 차이 출력 (UPDATE 미실행)
5. 사용자 검수 → 실제 실행 시 `--apply` 플래그로 UPDATE
6. UPDATE 후 audit_logs에 1건씩 기록 (주체: master, 변경 사유: "monthly payroll redesign 2026-05-02")

#### 스크립트 본체 요건
- 신 산식: 정규 월급제(`!tempWageType && wageType === "monthly"`) 시프트는 wage=0 누적 안 함. 시급/일급/임시만 `computeWageForShift` 누적.
- daily_closings.laborCost는 텍스트 박제 (점장이 수동 수정한 흔적 vs 시스템 자동 추정 구분 어려움) — `--apply` 시 모든 row 일괄 덮어쓰기. 점장 수동 수정분 손실 가능성 → dry-run에서 차이가 큰 row는 사용자가 별도 검토.
- 5월 외 과거 박제값(2025년~2026-04월)은 원칙상 미터치. 옛 산식이라도 옛 박제대로 두고, 이미 확정 월정산은 그대로 유지. (Phase 5 이후의 정산 화면에선 문제 발생 가능 — 후속 핸드오프 후보).

#### Push 흐름
1. Phase 5·6 코드 변경 (이미 완료)
2. 본 스크립트 추가 (Phase 5.5)
3. 5월 박제 건수 조회 → 0건이면 스크립트 미실행 즉시 push, 1건+이면 dry-run → 검수 → apply → push
4. push 후 부록 B에 "Phase 5.5 — 5월 박제 N건 재산출 (변경 평균 ±X원)" append

### 3.7 박제 안전망 폐기 (Phase 5 후속, 4월 정산 1755만 결함 대응)

**결함**: Phase 5 적용 후 `monthlyClosings.sumLaborByCompany` 박제 안전망(ratio 보정)이 옛 박제와 신 산식을 동시에 합산해 월급제 이중 계산 발생. 천호점 4월 미확정 정산 인건비가 매출 39.3M의 44.7%인 17.56M으로 표시(정상치 약 11~12M, +590만 부풀림).

수치 분해:
- 옛 박제 SUM(시급제 + 월급제 옛 산식) ≈ 1,100만~1,200만
- 신 산식 월말 일괄(김정란 270만 + 진재이 320만) = 590만
- 합 ≈ 17,556,577원 (실제 표시값과 일치)

원인은 Phase 5 이후 박제값 의미가 변경(시급제만 포함)됐음에도 박제 안전망의 "박제 SUM = shiftTotalCost 강제 보정" 전제가 그대로 남아있던 것.

**대응 (사용자 결정)**: 박제 안전망 ratio 보정 폐기. 항상 시프트 실시간 + 월말 일괄로 산출.

#### 코드 변경
- `server/routers/monthlyClosings.ts:322-342` ratio 보정 블록 제거
- `closedDateStrs` 매개변수 자체는 schedules JOIN 필터링 용도로 유지 (closed 일자만 합산)
- daily_closings.laborCost SUM 조회·`shiftTotalCost = snapshotTotal` 라인 삭제
- 헤더 주석 "Phase E 박제 안전망" 항목 삭제 또는 이력 노트로 격하
- 결과: `totalCost = shiftTotalCost + monthlyTotalCost` (시프트 실시간 + 월말 일괄)

#### 부수효과
- 일마감 박제는 일마감 화면 표시용으로 격하. 월정산은 daily_closings.laborCost를 SUM하지 않음.
- 시프트 사후 수정 시 박제값과 월정산 표시값이 어긋날 수 있음(현재는 ratio 보정으로 박제값 우선). 단, 시급제 한정의 드문 케이스 — 후속 핸드오프 후보.
- 과거 옛 박제값(2025~2026-04 daily_closings.laborCost)은 그대로 잔존. 이제 월정산 산출에 영향 없음. 일마감 화면에서만 옛 산식 박제값 표시.
- 이미 확정된 monthlyClosings 박제값은 미터치(과거 확정 데이터 무결성 보존).

#### 검증
- 4월 미확정 정산 인건비 = 시급제 시프트 누적(약 5~6M) + 월말 일괄(590만) ≈ 11~12M으로 정상화
- 5월(Phase 5.5 재산출 적용)도 동일 산식으로 일관
- LaborCostPage = MonthlySettlementPage 인건비 일치 (정책 §3.4 본래 의도)

### 3.5 계약서 박제 임금구성표 (1차 보고 의문점 해소)

### 7.1 운영자 시프트 누락 → 임금 자동 차감

- 달력일수 vs 소정근로일수 간 임금 차이 발생.
